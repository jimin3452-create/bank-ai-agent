# 01. 통합 기획서 — 은행 모바일 웹서비스 + 소비패턴 관리 AI Agent

> 상태: 초안 v0.1 (2026-11-05) / 작성: 김지민 + Claude
> 성격: 학습용 프로젝트. 실제 은행 시스템과 연결하지 않는다.
> 표기 규칙: **[기존]** = 기존 GitHub 기획서·DB 기준 / **[신규]** = 이번 프로젝트에서 추가 / **[신규 제안]** = 요청서에 없지만 보완 제안(검토 필요)

## 0. 한 줄 요약

기존 은행 4개 도메인(A 회원·인증, B 계좌, C 이체, D 카드)은 **그대로 유지**하고, 그 위에 **자연어 Agent(F)·소비패턴 관리(E)·RAG 안내(G)** 를 얹는다. 기존 테이블은 수정하지 않고 신규 테이블만 추가한다.

## 1. 원칙 (확정)

| # | 원칙 | 비고 |
|---|---|---|
| P1 | 기존 GitHub 저장소는 수정·덮어쓰기 금지 | 참고 전용, 사본은 `reference/` |
| P2 | 기존 기능 ID·FLOW·SCR·테이블은 임의 변경 금지 | 변경은 `02-기존대비-변경제안서.md`로 승인 후 |
| P3 | **숫자 계산은 도구(SQL/코드)가, 문장 생성은 LLM이** | 금액 환각 방지의 핵심 |
| P4 | Agent는 **로그인 사용자 본인 데이터만** 접근 | 기존 JWT 소유권 검사 재사용 |
| P5 | 돈이 움직이는 동작은 사용자 **최종 확인** 필수 | MVP는 "화면 이동+입력값 채움"까지 |
| P6 | 현재 단계는 문서만. 코드 구현 없음 | |

## 2. 프로젝트 목표 · 성공 기준

목표: **자연어로 은행 업무를 쓰고, 내 소비패턴을 분석·관리하는 AI Agent 은행 모바일 웹.**

| ID | 성공 기준(제안, 검토 필요) | 측정 방법 |
|---|---|---|
| G-N1 | 은행 기본 기능 A~D가 기존 명세대로 동작 | 기존 TC-F/E/S 통과 |
| G-N2 | 소비 질의 20종 시나리오에서 금액이 DB 집계값과 100% 일치 | 골든 질의셋 자동 대조 |
| G-N3 | 타 사용자 데이터 접근 시도 0건 통과 | 보안 TC (타인 ID 주입) |
| G-N4 | 후속 질문("그럼 지난달은?") 맥락 유지 | 멀티턴 시나리오 10종 |
| G-N5 | 소비 자동분류 정확도 목표 설정 | 라벨링 샘플 200건, 목표치는 검토 후 확정 |

## 3. 사용자

| 구분 | 기존/신규 | 주요 니즈 |
|---|---|---|
| 신규 가입자, 일상 이용자, 계좌 관리자, 자동이체·카드 이용자 | [기존] | 은행 기본 업무 |
| 소비 관리 이용자 (월급쟁이, 사회초년생) | [신규] | "이번 달 식비 얼마 썼지?", 예산·절약 |

## 4. 전체 기능 구조

```
A 회원·인증 [기존]   A1 가입 / A2 로그인·보안 / A3 계정관리
B 계좌 [기존]        B1 개설 / B2 조회 / B3 관리 / B4 해지 / B5 소유·상태검사
C 이체 [기존]        C1 즉시 / C2 자동(필수)·예약(선택) / C3 자주쓰는계좌 / C4 대량(선택)
D 카드 [기존]        D1 체크카드 / D2 신용카드(선택)
─────────────────────────────────────────────
E 소비패턴 관리 [신규]
  E1 자연어 소비내역 조회      E2 소비 자동 분류
  E3 소비패턴 분석            E4 소비 예산 관리
  E5 소비 변화 감지           E6 소비 예측
  E7 소비 개선 제안           E8 정기 지출 분석
  E9 이상 소비 알림 [신규 제안]   E10 월간 소비 리포트 [신규 제안]
F Agent 코어 [신규]
  F1 자연어 → 은행 기능 실행·화면 이동   F2 대화 맥락·후속 요청
  F3 안전장치(확인·PIN·권한)             F4 대화 이력 관리
G RAG 안내 [신규]
  G1 금융상품·약관·서비스 안내
```

상세는 `03-소비분석Agent-기능명세.md` 참고.

## 5. 시스템 아키텍처 (제안)

```
[모바일 웹 UI] ─ 채팅창 + 기존 화면(SCR)
      │ JWT
[기존 은행 API] ◄────── (조회/실행 요청, 소유권 검사 재사용)
      │
[Agent 서비스 (신규)]
   ├ Orchestrator: 의도분류 → Tool 선택 → 결과 요약
   ├ Tools: 소비조회/집계/예산/예측/화면이동/RAG검색 ...
   ├ Guard: 권한·확인·PIN·프롬프트 인젝션 방어
   └ Memory: 대화 이력, 최근 조회 조건(slot)
      │
[PostgreSQL] 기존 15개 테이블 + 신규 테이블 + pgvector(RAG)
[LLM API]   Tool Calling 지원 모델 / 임베딩 모델
```

| 영역 | 선택 | 구분 | 이유 |
|---|---|---|---|
| DB | PostgreSQL (기존) + pgvector | 기존+신규 | 별도 벡터DB 없이 학습용 구성 단순화 |
| 인증 | JWT (기존) | 기존 | Agent도 동일 토큰 사용 |
| Agent 서비스 | Python + FastAPI | 신규 제안 | LLM/RAG 생태계, 기존 백엔드와 분리 배포 |
| LLM 호출 | Tool Calling 방식 | 신규 제안 | 자유 SQL 생성 대신 **검증된 도구만 호출** |
| 기존 백엔드/프론트 스택 | 확인 필요 | 미확인 | `features/`·코드 미열람 — 연결 후 확정 |

## 6. 핵심 설계 결정

| # | 결정 | 이유 |
|---|---|---|
| D1 | LLM이 SQL을 직접 쓰지 않는다. 파라미터화된 집계 Tool만 호출 | 보안(인젝션)·정확도 |
| D2 | 카테고리는 별도 매핑 테이블로 관리 | 기존 `account_transactions` 비수정 |
| D3 | 분류는 **규칙 우선 → LLM 보조 → 사용자 수정 학습** | 비용·일관성 |
| D4 | 소비 = `OUT` 방향 거래 중 내 계좌 간 이동 제외 | 이체의 이중 집계 방지 |
| D5 | 기간 경계는 Asia/Seoul 기준 | TIMESTAMPTZ 월말 오류 방지 |
| D6 | 이체 실행은 화면 이동 + 입력 프리필 (직접 실행은 후속 단계 옵션) | 금전 사고 방지 |

## 7. 비기능·보안 요구 (제안)

| 항목 | 내용 |
|---|---|
| 개인정보 | LLM에 보내는 데이터는 최소화(계좌번호·이름 마스킹). 학습용이지만 실서비스 전환 시 금융 AI 관련 규정 검토 필요 |
| 감사 | 모든 Tool 호출은 `agent_action_logs`에 기록 |
| 응답 | 금액·건수는 Tool 반환값만 인용. 근거 기간/조건을 응답에 함께 표기 |
| 프롬프트 인젝션 | 거래처명·메모 등 사용자 입력 텍스트는 "데이터"로만 취급, 명령으로 해석 금지 |
| 성능 목표 | 응답시간·부하 목표는 기존 문서처럼 별도 설정 (미정) |

## 8. 범위

| 구분 | MVP | 후속 |
|---|---|---|
| 기존 | A~D 필수 기능 | 선택 기능(예약·대량이체, 신용카드) |
| 신규 | E1~E8, F1~F3, G1 | E9, E10, F 직접 이체 실행, 마이데이터형 외부 연동 |

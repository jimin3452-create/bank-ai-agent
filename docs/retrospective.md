# 회고

## 1. 배운 점
- **이체는 한 번만, 끝까지 되거나 아예 안 돼야 한다.** 이체를 하나의 트랜잭션으로 묶고 중복 방지 키와 계좌 잠금을 같이 썼다. 같은 요청이 두 번 와도 한 번만 처리되고, 동시에 여러 건이 와도 잔액이 꼬이지 않는 것을 테스트로 확인했다.
- **실패한 경우도 기록으로 남기고 테스트한다.** 잔액이 모자라면 오류만 돌려주지 않고 실패 이체로 남기되, 잔액과 거래내역은 바뀌지 않게 했다.
- **AI에게 맡기는 범위를 좁혔다.** AI가 다듬은 답변은 숫자가 원래 값과 같을 때만 쓴다. 이체나 카드 분실처럼 위험한 일은 AI가 직접 하지 않고 화면으로 안내하며, PIN은 사용자가 직접 입력한다.
- **질문 세트를 만들어 두면 AI 품질을 숫자로 비교할 수 있다.** 프롬프트를 바꿀 때마다 좋아졌는지 바로 알 수 있었다.

## 2. 어려웠던 점과 해결 과정
- **AI가 질문 5개를 틀렸다(46/51).** 출금 방향, 카테고리, 받는 사람 같은 값을 빼먹거나, "방법을 묻는 질문"을 실행 요청으로 착각했다. 프롬프트에 규칙과 예시를 넣어도 3개만 고쳐졌다.
  - 원인은 출력 형식이었다. 값이 없어도 되는 항목은 AI가 애매하면 아예 건너뛰었다. 모든 항목을 필수로 하고 값이 없으면 null을 넣게 바꾸니 50/51이 됐다.
  - 마지막 1건은 AI가 틀린 게 아니었다. AI는 이유 설명과 해제 안내를 둘 다 했는데, 평가가 첫 번째만 봤다. 평가 기준을 고쳐 51/51을 맞췄다.
- **제출 당일 테스트 1개가 실패했다.** 앱 문제가 아니라 테스트 안에 날짜(11월 10일)가 박혀 있었다. 오늘 날짜를 쓰게 고쳐서 167개 전부 통과했다.
- **내 PC의 PostgreSQL과 포트가 겹쳤다.** Docker 쪽 포트를 5433으로 바꿨고, 이 내용은 README에 적었다.

## 3. 남은 한계
- 화면(프론트엔드)은 자동 테스트가 없고, 제출 직전에 전체 화면을 다시 확인하지 못했다.
- 에이전트 테스트는 가짜 AI로 돌렸다. 실제 Gemini 평가(51/51)는 평가 기준을 한 번 고친 뒤의 점수이고, 제출 직전에는 다시 돌리지 않았다.
- 거래내역이 Gemini로 전송되므로 가상 데이터로만 써야 한다. 실제 고객 데이터에는 쓸 수 없다.
- 테스트용 JWT 키가 짧다는 경고가 뜬다. 실제 서비스에서는 32바이트 이상으로 바꿔야 한다.

# 06. RAG 설계 — 금융 상품·약관·서비스 안내

## 0. 한 줄 요약
RAG는 **"규정·상품·사용법 질문"** 에만 쓰고, **내 계좌·내 소비 숫자**는 RAG가 아니라 DB Tool로 답한다. 두 경로를 의도 분류에서 나눈다.

## 1. 라우팅 규칙

| 질문 유형 | 예 | 경로 |
|---|---|---|
| 내 데이터 | "내 이번 달 식비" | DB Tool (E/F) |
| 상품·규정·사용법 | "입출금통장 금리", "해지 조건", "자동이체 말일" | RAG (G1) |
| 혼합 | "내 계좌로 해지할 수 있어?" | DB Tool(잔액·연결서비스) + RAG(해지 규정) → 결합 응답 |

## 2. 지식 소스

| 소스 | 원천 | 구분 | 비고 |
|---|---|---|---|
| 계좌 상품 | `account_products` (상품명, 금리, 설명) | [기존 데이터] | 변경 시 재색인 |
| 약관 | `terms` (제목, 내용, 버전, 필수여부, 분류) | [기존 데이터] | 버전 메타데이터 보존 |
| 서비스 이용 가이드 | 기존 기획서의 기능·정책(한도, 상태별 허용 동작, 해지 조건 등)을 사용자용 문장으로 재작성 | [신규] | 내부 기획 용어 제거 |
| FAQ | 가입, 인증, 이체 한도, 자동이체, 카드 분실 등 | [신규] | 20~30개로 시작 |
| 소비관리 사용법 | 예산·분류·예측 설명, 예측의 한계 | [신규] | |

주의: 기획서의 **미정 정책**(잠금 임계값 등)은 가이드에 넣지 않는다. 확정 전에는 "정책 확정 전" 상태로 두거나 제외.

## 3. 수집·가공 파이프라인

```
원천(DB/마크다운) → 정제(HTML·불필요 문구 제거)
 → 청킹(제목 단위 + 500~800자, 문단 겹침 10~15%)
 → 메타데이터 부여(doc_type, title, version, source_id, section)
 → 임베딩 → rag_chunks 저장 → 인덱스
```

| 항목 | 제안 | 이유 |
|---|---|---|
| 청킹 | 약관은 조항 단위, FAQ는 질문-답 1쌍 단위 | 조항이 중간에 잘리면 오답 |
| 재색인 | 원천 변경 시 해당 문서만 | `version`/`updated_at` 비교 |
| 아카이브 | 구버전 약관은 `ARCHIVED`, 기본 검색 제외 | 최신 약관 우선 |

## 4. 검색·응답

| 단계 | 내용 |
|---|---|
| 쿼리 정리 | 대화 맥락 반영해 단독 질의로 재작성 ("그건?" → 풀 문장) |
| 검색 | 벡터 검색 상위 8 → 키워드(BM25/FTS) 병합 → 상위 4~5 선택 |
| 필터 | `status=ACTIVE`, 질문 유형에 맞는 doc_type |
| 임계값 | 유사도 낮으면 "문서에서 확인할 수 없습니다" |
| 응답 | 근거 문장 요약 + **출처(문서명·버전)** 표기 |
| 금지 | 문서에 없는 금리·수수료·조건을 추측해 답변, 가입 권유 |

응답 템플릿:
```
[핵심 답변 1~2문장]
근거: <문서명> v<버전> — <핵심 조항 요약>
※ 학습용 서비스 안내이며 실제 금융상품이 아닙니다.
```

## 5. 평가

| 지표 | 방법 | 목표(초안) |
|---|---|---|
| 검색 적중률 | 질문 40개 × 정답 청크 지정, top-5 포함 여부 | 검토 후 확정 |
| 답변 근거성 | 응답이 검색 청크 내용만 사용했는지 수동 샘플 점검 | |
| 거절 정확성 | 문서에 없는 질문 10개에서 "확인 불가" 응답 | |
| 혼합 질의 | DB+RAG 결합 시나리오 5개 | |

## 6. 선택지 (결정 필요)

| 쟁점 | 선택지 | 제안 |
|---|---|---|
| 벡터 저장소 | pgvector / 별도 벡터DB | **pgvector** (기존 PostgreSQL 활용, 학습용 단순화) |
| 검색 방식 | 벡터만 / 하이브리드 | **하이브리드** (상품명·조항번호는 키워드가 강함) |
| 임베딩 모델 | 한국어 지원 모델 선택 | 모델 확정 후 벡터 차원 결정 (04 문서 `rag_chunks.embedding`) |

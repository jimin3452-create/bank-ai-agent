# 02. 기존 설계 대비 변경·충돌 제안서

> 목적: 기존 기획서·DB와 **충돌하거나 변경이 필요한 사항**을 이유와 함께 모아 사용자 승인을 받는다.
> 기존 설계는 이 문서의 승인 전까지 **한 줄도 바꾸지 않는다.**
> 근거 자료: `product-spec.md` 요약, `term-mapping.md`. SQL 원본·`features/`는 미열람 → 해당 항목은 "확인 필요"로 표기.

## 0. 요약

| 구분 | 건수 |
|---|---|
| 기존 변경 없이 신규 추가만으로 해결 | 다수 (04 문서 참조) |
| **기존 정의 변경(코드값 추가 등) 필요** | 2건 (C-01, C-02) |
| 기존 미정 정책 확정이 필요한 의존 | 5건 (C-03~C-07) |
| 설계 선택(변경 아님, 승인 요청) | 5건 (C-08~C-12) |

## 1. 변경 요청 (기존 정의에 영향)

| ID | 대상 | 현재(기존) | 제안 | 이유 | 영향 | 승인 |
|---|---|---|---|---|---|---|
| C-01 | `notifications.type` 코드값 | CARD_PAYMENT, SUSPICIOUS_LOGIN, AUTO_TRANSFER_FAIL | **BUDGET_ALERT, SPENDING_ANOMALY, MONTHLY_REPORT 추가** | 예산 초과·이상소비·리포트를 기존 알림 화면에 노출 | 코드값 추가뿐, 컬럼 변경 없음. CHECK 제약이 있다면 수정 필요(SQL 확인) | ☐ |
| C-02 | 알림 목록 화면(SCR 확인 필요) | 3종 유형 표시 | 신규 3종 표시 | 위와 동일 | 프론트 유형 매핑 추가 | ☐ |

## 2. 기존 미정 정책에 의존하는 항목 (확정 필요)

| ID | 기존 미정 정책 | Agent 쪽 의존 | 임시 가정(확정 전) |
|---|---|---|---|
| C-03 | A2.1 로그인/PIN 잠금 임계값 | Agent 확인 단계의 PIN 오입력 처리 | 기존 `pin_fail_count` 정책을 **그대로 공유**, Agent용 별도 카운트 없음 |
| C-04 | B3.3.1 계좌 비밀번호 실패→거래중지 기준 | Agent가 실행하는 이체 시 계좌 비번 처리 | MVP는 화면 이동이라 Agent가 비번을 받지 않음 |
| C-05 | 계좌 상태별 허용 동작(제안표, 규정검토 필요) | SUSPENDED/CLOSED 계좌의 소비 분석 포함 여부 | 조회 허용 상태이므로 **분석 포함**, 쓰기성 동작은 차단 |
| C-06 | A3 탈퇴 제한 정책 | 탈퇴 회원의 소비·대화 데이터 보존 기간 | 탈퇴 시 Agent 데이터 함께 삭제(제안) |
| C-07 | C2.1 말일 처리 | 정기지출 예상일 계산 | 말일 초과일은 해당 월 말일로 보정(동일 규칙 적용 제안) |

## 3. 설계 선택 (변경은 아니지만 승인 요청)

| ID | 쟁점 | 선택지 | **제안** | 이유 |
|---|---|---|---|---|
| C-08 | 소비 카테고리 저장 | ① `account_transactions`에 컬럼 추가 ② 별도 매핑 테이블 | **② 별도 테이블** | 기존 테이블 무변경 원칙(P2). 재분류 이력 관리 용이 |
| C-09 | 소비 판정 | 모든 OUT = 소비 vs 내 계좌 간 이체 제외 | **내 계좌 간 이체 제외** | 이체는 서비스 내 계좌 간만 가능 → `counterparty_account`가 내 `accounts.account_num`이면 소비 아님 |
| C-10 | 카드 소비 데이터 출처 | `card_payments` vs `account_transactions` | **`account_transactions`(type=CARD) 기준** | 가맹점명이 `counterparty_name`에 이미 복제됨(term-mapping 근거), 계좌 거래 단일 원천 |
| C-11 | Agent 이체 실행 | 직접 실행 / 화면 이동+프리필 | **MVP는 화면 이동+프리필** | 금전 행위는 기존 C1 검증·PIN 흐름 그대로 사용, 사고 방지 |
| C-12 | 다중 계좌 | 계좌별 / 전체 합산 | **기본 전체 합산, 계좌 필터 지원** | 사용자 질의 자연스러움 |

## 4. 확인 필요 (SQL 원본 미열람)

| # | 확인 사항 | 이유 |
|---|---|---|
| V-1 | `account_transactions(account_id, transaction_at)` 인덱스 존재 | 집계 성능 |
| V-2 | `notifications.type` CHECK 제약 여부 | C-01 영향 |
| V-3 | `account_transactions.transaction_type` 값 중 소비 해당 범위 (WITHDRAW, TRANSFER, AUTO_TRANSFER, CARD) | 소비 정의 |
| V-4 | 카드 결제 시 `account_transactions` 행 생성 방식(트리거/서비스) | 분류 시점 |
| V-5 | `features/` 폴더 상세 문서의 기능 ID 체계 | 기능 ID 충돌 방지 (신규는 E/F/G 사용) |

## 5. 승인 체크리스트

- [ ] C-01, C-02 알림 코드 추가 승인
- [ ] C-03~C-07 임시 가정 승인 (또는 기존 정책 먼저 확정)
- [ ] C-08~C-12 설계 선택 승인
- [ ] V-1~V-5 확인용 `reference/` 파일 제공

## 6. 충돌 없음 확인 (기존 유지 항목)

기존 도메인 A~D 기능 ID, FLOW-001~010, SCR-001~013, 테이블 15개의 컬럼·코드값, 기존 정책(비밀번호·PIN·카드번호 암호화, 중복 제출 차단, 이체 원자성, 서비스 내 계좌 간 이체)은 **모두 유지**한다.
